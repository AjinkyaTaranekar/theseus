# #148: Measure Jev on the whole demo world

**Status:** proposed design for local review; no benchmark implementation or new measurement yet.
**Branch:** `jev-numbers`. **Audited main:** `591d0aaa42ecaee096a39b46d8c227ad2b0deac4`.
**Audit date:** 18 October 2026. [Issue](https://github.com/AjinkyaTaranekar/theseus/issues/148).
[Every issue and PR, integration status and handoffs](../reviews/148-board.md).

## The feature

A reproducible, offline-first evaluation of the raw sensitivity predictions on every `Resource` node in a
pinned demo world. Humans own the answers. The production Jev and fast-LLM fallback answer the same questions
through the existing wrappers. The evaluator computes accuracy, confusion by class, probability quality where
available, latency and every miss. A dated README block is generated from retained artifacts, without another
model call. No score changes a graph fact, override, recommendation, verdict or golden answer key.

This document settles a proposed implementation, not a new product specification. Decisions in the review
section below must be accepted before implementation; no production prompt or frozen contract changes are
needed for the recommended scope. Approval of this design does not mark #148 complete.

## Why it matters and what already exists

Spec 06 reports 9/10 sensitivity matches on `jev-1.13.0` and separately 13/14 steering attacks. A2's rationale
and the plan also mention a different 30/30 PoC experiment. Those samples cannot be combined or represented as
a whole-world evaluation. `README.md` has engine/demo timings and an S2 placeholder, but no Jev evaluation.

Source inspection and a local import of `fixtures/intern/base` at the audited commit found:

- 137 Terraform resources, 86 graph nodes, **22 Resource nodes**, in six categories. The denominator is 22,
  not 137, 86, ten or the number of overrides. Discover it again at execution time; never hardcode it.
- Two top-level sensitivity recordings contain **13** distinct answers: ten in
  `sensitivity-38b5f02e4cbd.json` and three in `sensitivity-4f9306d7b906.json`. Nine Resource nodes are unrecorded.
- Every file in that fixture's base snapshot matches the corresponding current `demo-infra/` file.
- `agent/sensitivity.classify` supplies sorted `(id, plain category name, name)` tuples. `Jev.sensitivity`
  builds the canonical question and caches each resource for the life of that client.
- `Jev.ask` records under a hash of the model, state and questions. Repeated identical requests in one
  directory overwrite that same filename. Its `ms` measures the successful transport attempt; it excludes
  earlier retries and backoff. The fallback's `ms` also excludes any preceding failed Jev attempts.
- The existing fallback produces a class and `source=fallback, calibrated=false`, with **no probability
  vector**. `JevAnswer` permits empty vectors and does not validate their range or sum.
- `ReplayedJev` combines historical answers by node ID for demos. That is useful product replay but cannot
  establish an exact benchmark request, complete coverage, fresh latency or a measured fallback comparison.

## Questions and the two providers

Use production `classify(nodes, jev)`, which calls `Jev.sensitivity`. Send only ID as the question key and the
production name/kind/context, with the existing four criteria. Do not send gold labels, overrides, old
predictions, graph sensitivity fields, IAM paths, repository comments, PR text or advisory text. This is
name/kind classification, not a new context-enriched classifier. Do not change the prompt to improve scores.

A small benchmark-local subclass of `Jev` observes the public `ask` result: delegate to `super().ask`, retain
its `JevReply`, return it unchanged. This captures request key, actual model and transport timing while
reusing the real sensitivity builder. It must make exactly one `ask` per batch and retain safe error metadata if `super().ask` raises.
Use a context-managed injected HTTP client for the Jev arm so fresh samples do not leak connections; only
the Jev wrapper performs transport calls. No direct HTTP/LiteLLM calls,
private `_live`/`_fallback` calls, new adapter protocols or copied prompt definitions are needed.

| Row | Construction | Provenance requirement |
| --- | --- | --- |
| Jev | Real `Jev` in record mode with **no LLM fallback supplied** | Every answer is `source=jev`; unavailable Jev produces a failed sample, never a fallback disguised as Jev |
| Fast LLM fallback | Separate settings copy with `typesafe_api_key=None`, `Jev(..., llm=Llm(...))` | Uses the existing deliberate missing-key fallback, makes zero Jev HTTP calls, calls `Llm.call(..., fast=True)`, every answer is `source=fallback, calibrated=false` |

The deliberate fallback is a controlled comparison, not an observed production outage. Pass the same sorted
22-resource batch in each arm. Each arm's settings keep their configured model names; record the returned
model separately, since `jev-latest` can resolve differently. Require the two settings keys before starting
a complete record run. Read secrets only through `Settings`; never serialize settings, credentials or
headers. Synthetic resource names are inputs, not actual credential values.

Validate exactly one typed choice for every requested resource and no extra answers. Invalid/missing answers
are explicit errors, never replaced by an override or counted correct. Preserve wrapper `ModelError`s and
error counts; do not catch an error and declare a successful evaluation. Errors contain provider/sample/key
and a safe reason, with no raw settings, server bodies or credentials copied into reports.

## Probability metrics and the fallback decision

Score the returned **raw choice**, before `apply` or overrides. Primary accuracy is `correct / total corpus
resources`; also show valid-answer coverage and failure count. A provider error does not reduce the
resource denominator. Confusion rows are human truth, columns predicted class, in alphabetical class order
(`confidential`, `internal`, `public`, `regulated`), with zeros for absent classes. Invalid/missing answers
have a separate error column. Per-class recall uses that class's human support; absent support is N/A.

For Jev, accept a probability vector only when all four keys are present, each value is a finite number
(not a boolean), each lies in [0, 1], and their sum differs from 1 by at most 1e-6. Never renormalize, fill
missing classes with zero, substitute `confidence`, fabricate one-hot vectors or repair NaN/Infinity.
Choice must be in the existing class set; preserve it even if it disagrees with the vector's argmax and
report that disagreement. Require valid vectors for the full corpus before publishing a whole-world Jev
Brier number. Diagnostic reports may show N/A with the exact valid-vector count and errors.

Use multiclass Brier **without dividing by the number of classes**:

`Brier = (1/N) * sum_over_resources(sum_over_four_classes((p[class] - 1[truth=class])**2))`.

Its range is 0 to 2, lower is better. A perfect answer scores 0, a confidently wrong answer 2, and the uniform
four-class distribution 0.75. For truth `confidential`, probabilities public=.1, internal=.2,
confidential=.6, regulated=.1 score .22. Pin these hand-worked values in tests. Keep full precision in JSON;
round only for the table. Brier measures probability quality on this corpus; it does not prove calibration.
The existing `calibrated=true` flag records Jev provenance, not independent proof of calibration here.

**Recommended fallback row:** accuracy, confusion, misses and latency use the same protocol, while Brier says
**N/A — production fallback returns labels only (0/N vectors), uncalibrated**. This honestly measures the
existing product. If both humans require a numeric fallback Brier, first approve a separate probability-vector
tool/prompt change in spec 06 and `agent/jev.py`, its provenance and regression tests. That would evaluate a
changed fallback; do not present it as the current label-only production behavior. Do not turn four yes/no
questions into a class probability distribution. This design does not authorize that prompt change.

## Sampling, latency and retained evidence

A proposed full run has one warmup and **20 measured whole-world requests per provider**, sequentially with
alternating provider order by sample number. That is **42 logical model calls**, before wrapper retries,
with 22 questions per request on this revision. No parallel load, opportunistic caching or best-run selection.
The command prints this budget before its explicit model-call confirmation. A future corpus above the wire
limit must fail with a useful error rather than quietly change the batching protocol.

Create a fresh observed Jev client per sample so its sensitivity cache cannot turn repeated samples into
zero model calls. Warmups use the same request but are flagged and excluded from metrics. Fix measured sample
001 as the primary accuracy/confusion/Brier/misses table **before** running. Report the other 19 samples'
accuracy/Brier ranges and class changes too; list every miss/error in every sample. Twenty repeated batches
are still **22 distinct resources**, never 440 independent examples. Do not retry until a flattering run appears.
Only the wrappers perform their documented retries; one failed logical sample remains a failure.

Measure end-to-end elapsed time with an injected monotonic timer around `classify`, including transport,
wrapper retries/backoff and response validation, but excluding world loading, gold loading, client setup and
report generation. Record mode includes recording I/O; state that explicitly. Retain the wrapper's reported
`ms` separately as successful-attempt/provider time. Do not mix the two spans. The forced-fallback arm does
not include a deliberately induced Jev outage or its backoff. These are full-batch latencies, not per-resource
latencies and not engine, PR, database or guest-box latency.

Use nearest-rank percentiles on successful measured full-batch calls: `sorted_ms[ceil(p*n)-1]` for p=.50/.95.
At n=20, p95 is the 19th sorted sample. Show n and failures next to p50/p95. An incomplete run may produce a
diagnostic artifact, but cannot replace a completed README measurement. Never calculate fresh latency by
timing replay. Store all new elapsed values/aggregates inside benchmark-local `Timings` models; keep original
wrapper recording formats intact. Use no automatically generated wall-clock timestamps or random IDs.

The caller supplies `--run` and `--as-of YYYY-MM-DD`; create a new, previously nonexistent run directory.
A reused run name fails before writing or calling a model. This avoids overwriting failures or measurements.
Each sample uses a distinct directory, keeping the existing exact request-hash filenames:

```
recordings/jev/bench-148/<run>/jev/sample-001/<sensitivity-hash>.json
recordings/jev/bench-148/<run>/fallback/sample-001/<sensitivity-hash>.json
recordings/llm/bench-148/<run>/fallback/sample-001/<sensitivity-fallback-hash>.json
bench/jev/runs/<run>/manifest.json
bench/jev/runs/<run>/results.json
bench/jev/runs/<run>/report.md
```

Warmups use `warmup-001` directories. Jev wrapper records for the fallback explicitly identify its source;
the matching LLM recording is retained too. Existing top-level recordings are untouched. Exact replay uses
these sample directories and their request hashes, never `ReplayedJev` or a glob that pools old node-ID answers.

The immutable manifest records schema/protocol version, caller-supplied date and run name, source/code SHA,
source/plan/corpus/labels/prompt hashes, input paths, class supports, resource/category/skip counts, configured
and returned model IDs, arm order, warmups/repeats, recording paths and SHA-256 digests, timing span, percentile
rule and probability rule. Put each input digest beside its path. `results.json` holds every sample's typed
prediction, provenance, probabilities, metrics, misses/errors and `Timings`; no model prose is needed.
Record the environment (Python/platform and installed wrapper library versions), not a host IP or user path.
Record from a committed evaluator/classifier revision and reject dirty evaluator, classifier or corpus inputs;
human labels are pinned by their separate digest. Documentation-only changes do not change model questions.

`report` verifies hashes, label/corpus agreement, source revision, sample counts and completeness, then
recomputes the metrics from recordings and retained timings. Re-rendering is byte-stable. Missing/tampered
recordings, drifted inputs, mixed Jev model versions or missing source provenance reject publication with a
clear reason. A diagnostic report remains available for incomplete runs. A homogeneous historical manifest
may be re-rendered after a model alias advances without calling the new model. The collection SHA identifies
the evaluated code tree; verify the pinned file contents rather than requiring it to equal current HEAD.
A later commit that adds results/docs must not invalidate unchanged evaluator/classifier/corpus hashes.

## Commands and implementation files proposed for review

Keep executable code and artifacts under `bench/jev/`. The issue names `bench/jev.py` but also asks for this
work to stay under `bench/jev/`; use a package entry point **`python -m bench.jev`**. Python's namespace
package works with the current tree and S2's pending tree, and also works if `bench/__init__.py` is introduced
later. Do not add competing module/package entry points or change S2's runner, case plans or top-level report.

Proposed interface (examples, not commands available today):

```bash
python -m bench.jev inventory --world fixtures/intern/base --plan fixtures/intern/base.plan.json
# Humans review the inventory and save bench/jev/labels.json themselves.
python -m bench.jev validate --labels bench/jev/labels.json
THESEUS_MODE=record python -m bench.jev record --run demo-2026-10-18 --as-of 2026-10-18 --warmups 1 --repeats 20 --confirm-model-calls
python -m bench.jev report --run demo-2026-10-18 --check
python -m bench.jev report --run demo-2026-10-18 --write-readme
```

`validate`/`record` default to the displayed world/plan and explicit human label path. `record` requires
`THESEUS_MODE=record` and the explicit confirmation flag; ordinary inventory, validate, report and tests
cannot instantiate network clients. A smoke run with fewer repeats stays diagnostic and cannot write the
README. The renderer writes only its own marked README block, checks exactly one marker pair, refuses
unrelated edits, and does not run models. `--check` compares regenerated JSON/Markdown and exits nonzero on
drift. No default command updates gold labels.

## Test-first implementation slices

1. **Corpus/key:** write failing tests for discovery of all Resource nodes, duplicates, changed names/kinds,
   missing/extra/invalid labels and no network on any validation failure. Include a tiny synthetic graph for
   exact expectations, plus a current-world coverage assertion derived from the real importer.
2. **Metrics:** write hand-worked accuracy/confusion/Brier cases, absent classes, malformed vectors, missing
   answers, nonfinite/bool values, no normalization, percentile ranks and warmup exclusion. Verify overrides
   cannot make an incorrect prediction correct. Pin primary sample selection independently of outcomes.
3. **Collection:** fake transports/LLM/timers prove one identical batch per sample, fresh clients, distinct
   directories, 42 logical calls for the full protocol, no Jev HTTP in the fallback arm, actual provenance,
   failed samples retained, and no credentials printed. Production sensitivity/cache/fallback tests stay green.
4. **Artifacts/report:** tests for exact replay, byte-stable generation, hash mismatches, reused run rejection,
   missing recordings, mixed models, corpus changes, incomplete runs, latency source and restricted README
   replacement. Prove `report`/`--check` cannot call the network or write labels.
5. **Human key/live:** obtain the reviewed key first; then an explicit record run using real providers. Commit
   the actual recordings with the tests that replay them. Inspect all misses; change neither key nor prompt
   to improve the score. A label correction needs humans and a separately identified rerun/provenance change.
6. **Publication:** generate the dated table/report, list every miss, run offline tests and Ruff, and have both
   humans review the artifacts/diff. Push only when the user later authorizes it.

`pytest -m live` by itself still skips live tests in this repo. An intentional live smoke test needs
`THESEUS_LIVE=1 THESEUS_MODE=record python -m pytest -q -m live tests/integration/test_jev_bench_live.py`.
Default tests use `_env_file=None`, fake transports and temporary directories; no keys or `.env` are needed.
The CLI record confirmation and the pytest live gate are separate entry points. Do not change global test
selection or allow default replay tests to switch to live via a local `.env`.

## README result contract and done when

Generate a marked block headed with the caller-supplied date, commit, corpus/label hashes and **N distinct
modeled resources**. Include a table with provider/actual model, raw correct/N, answer coverage, Brier and
vector coverage, whole-batch p50/p95 milliseconds, measured batches/failures, and provenance. Fallback must
say uncalibrated and label-only. Link the report, which includes the full confusion matrix, per-class support,
all sample results, all misses/errors and replay command. No numeric cells are filled in by this design.

Beside it preserve the separate historical steering result: **13/14 attacks detected, 0/17 ordinary PRs
flagged on that 31-case evaluation**, at threshold .5, `jev-1.13.0`, linked to spec 06. Its miss is the title
JSON breakout (.32). Do not relabel it as this run, silently change its denominator to the now-larger intent
fixture set, or describe sensitivity Brier as a test of steering/urgency/breakage calibration.

- [ ] Both humans accept the proposed decisions and own/save all gold labels.
- [ ] Exactly the discovered full corpus is scored with raw predictions, no override leakage.
- [ ] Both real provider arms retain full requests/responses and actual model provenance.
- [ ] Jev Brier has complete valid vectors; fallback N/A is explicitly approved, or a separately approved
  probability-capable fallback is evaluated under a distinct protocol.
- [ ] Primary metrics, complete confusion, every miss/error and the full sampling protocol are retained.
- [ ] Repeated requests do not overwrite; p50/p95 use recorded live batch latency, with sample/failure counts.
- [ ] `report --check` reproduces artifacts offline; the README block is generated, dated and scoped to N.
- [ ] New tests first failed, then passed; full offline pytest, Ruff and diff checks pass; no golden keys or
  answer keys were changed by an agent; real recordings are committed with their replay tests.
- [ ] AI disclosure distinguishes agent work from human labeling/review; both humans read the diff.
