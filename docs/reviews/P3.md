## The ideas you need to explain

- An actor is a user, workflow, workload, or the internet.
- A role is an identity with permissions; group membership can give a user permission to assume one.
- A path is the chain showing how an actor reaches data.
- A requirement records access someone legitimately needs. R1-R17 come from configuration; I1 comes from a PR's stated intent.
- A dangerous path reaches sensitive data that is not covered by that actor's requirements.
- Reading a database secret creates an inferred `UNLOCKS` path to its database. This is a modeled assumption, not proof that network access or an exploit succeeds.
- `CALLS` records what code uses. It does not itself grant permission. `REQUESTS` to another service does not inherit that service's IAM access.
- A capacity is a cost used to choose a cut. It is not bandwidth or a number of users.

Sensitive data is classified confidential or regulated. The scenario counts assume the intended sensitivity labels are present; A2 must verify them or humans must provide overrides.

## 1. Intern: onboarding grants too much

### Before and after

Before: Priya has no support-group membership and no route to its role or data. Sam already belongs to the group.

After: one new membership is added. The intended outcome is only access to application logs:

```text
user:priya-intern
  --MEMBER_OF--> group:support-engineers
  --CAN_ASSUME--> role:prod-support
  --CAN read--> s3://demo-app-logs/       legitimate: I1
```

The same role also opens three dangerous actor/target pairs:

```text
Priya -> support-engineers -> prod-support -> invoices/          read
Priya -> support-engineers -> prod-support -> prod-db-credentials read
Priya -> support-engineers -> prod-support -> prod-db-credentials
      -> customer-db                                             read/write, inferred
```

The third route uses `UNLOCKS` from the secret to the database. The secret and database count separately, even though their routes share edges. Reading logs is new access but is not a dangerous path because I1 covers it.

Expected: 3 opened dangerous pairs, 0 closed, and 6 baseline pairs unchanged. In head, R1-R17 and I1 are satisfied. I1 is missing in base because Priya does not yet have access; that is the intended onboarding change.

Evidence to inspect later: `terraform/people.tf` membership `aws_iam_user_group_membership.priya_support`; `aws_iam_group_policy.support_assume` / `AssumeProdSupport`; `terraform/roles.tf` trust `TrustAccountPrincipals` and grants `ReadLogs`, `ReadInvoices`, `ReadDbSecret`; `terraform/data.tf` secret's `db_instance` tag.

### Candidate fixes

| Candidate | Expected verdict | Why |
| --- | --- | --- |
| A: remove Priya's membership | fail | Removes the dangerous paths but also removes her required log access, I1. |
| B: give Priya a new logs-only `intern-onboarding` role and remove her group membership | pass, recommended by the scenario | Priya retains logs through the new role; she no longer reaches the support role. Sam's access is unchanged. |
| C: add a deny conditioned on Priya's identity | unknown | The condition is outside the supported IAM subset. The engine cannot certify it. |
| D: remove the support group's `AssumeProdSupport` statement | fail | Breaks Sam's R1-R3 and Priya's I1. The deployment role's separate assume statement is not this statement. |

The PR check initially fails; applying a verified B makes this scenario's check succeed. B does not eliminate the six unrelated baseline findings.

## 3. Compromised Action: a preview workflow can reach production

The advisory matches `demo-thirdparty/file-diff@v3` in both preview and lint workflows. Treat compromise as an explicit assumption.

- `docs-site/preview.yml` can request an ID token. Its subject `repo:demo-org/docs-site:pull_request` matches the overly broad trust `repo:demo-org/*` on `github-deploy`.
- `website/lint.yml` cannot request an ID token, so it has no `TRUSTS` edge and reaches no cloud data through this model.

The preview's authorization paths are:

```text
preview.yml --TRUSTS--> github-deploy --CAN_ASSUME--> prod-support
  --CAN read--> invoices/

preview.yml --TRUSTS--> github-deploy --CAN_ASSUME--> prod-support
  --CAN read--> prod-db-credentials --UNLOCKS read/write--> customer-db
```

Blast radius: invoices, DB secret, customer database. These are already present in main; an advisory does not add a new Terraform permission.

The narrative trace from the Action to the database has five hops. Its first hop goes backward along the workflow's `USES` relationship to identify the workflow. The valid permission path begins at the workflow and has four hops. `USES` is not traversed by the authorization-path query.

`terraform-apply` remains unreachable from preview because it requires the exact subject `repo:demo-org/infra:environment:production`. The Terraform state bucket and payment key are outside this finding's modeled blast radius.

Minimum-cut value: 1 on `preview.yml --TRUSTS--> github-deploy`. The downstream migration access is protected by legitimate deployment requirements.

Containment K restricts `github-deploy` to `repo:demo-org/infra:ref:refs/heads/main`. That preserves the deployment release job while rejecting preview. R4, R5, R17, and the other baseline requirements remain satisfied.

Important wording distinction: this uses the same *pinning approach* as `terraform-apply`, but not the same literal subject. The deployment release job uses the main-branch subject; its apply job uses the production-environment subject.

Expected rotation list: only `secret:prod-db-credentials`. The database and invoices are affected data, not extra secrets to rotate. Containment stops the route; rotation addresses potentially exposed credentials.

Preview is labeled staging and its targets prod, so this is also a staging-to-production finding. The spec expects `prod-support` to rank first among roles by betweenness; actual algorithm output and numeric scores need later verification, not a P3 claim of a runtime result.

After K, preview's 3 dangerous pairs close. The deploy-to-invoices pair and support-portal's 2 pairs remain: 3 baseline pairs in total.

Evidence to inspect later: the preview/lint `uses` and `permissions` lines; `terraform/ci.tf` OIDC subjects and `AssumeProdSupportForMigrations`; `terraform/roles.tf` data grants; secret's database tag.

## 4. Unused grant: support-portal has a leftover secret permission

This is a scan of main, not a before/after PR.

```text
workload:support-portal --RUNS_AS--> role:support-portal
  --CAN read [LegacyDbSecret]--> secret:prod-db-credentials
  --UNLOCKS read/write--> db:customer-db
```

Support-portal uses billing-api and orders-api over HTTP. Its baseline code has no secret call or database connection, and there is no declared requirement for direct database access.

Expected: 1 unused grant produces 2 dangerous actor/target pairs, one for the secret and one for the database.

Capacity sketch: `RUNS_AS` = 1,000,000; unused secret `CAN` = 1; `UNLOCKS` = 1,000,000. The minimum cut therefore costs 1 and selects the unused secret grant.

Candidate U removes `LegacyDbSecret`. Expected pass: both dangerous pairs close, all R1-R17 remain satisfied, and no modeled code call loses access. The remaining baseline dangerous pairs number 4.

Do not flag billing-api's required and called secret access, billing-job's required/called grants, or the shared orders-table grant used by both ECS workloads. Required edges get BIG capacity even if they are also used by code; USED = 1,000 applies only when the edge is not already protected as required.

Evidence to inspect later: `terraform/services.tf`, `aws_iam_role_policy.support_portal`, Sid `LegacyDbSecret`; support-portal's code-call inventory and skipped/unresolved-call coverage. Absence of a modeled call is bounded by the code reader's documented capabilities, not proof about arbitrary real-world runtime behavior.

## 5. Code PR: a claimed typo fix starts using existing access

The PR says it fixes "recieved" to "received". It also adds an export endpoint, code that reads the DB secret and connects to the customer database, and the `DB_SECRET` environment variable. No IAM grant is added.

Before: support-portal can reach the secret and database through `LegacyDbSecret`, but does not call them.

After: the authorization paths are unchanged. Two new code uses appear:

```text
workload:support-portal --CALLS read--> secret:prod-db-credentials
workload:support-portal --CALLS db:connect/read--> db:customer-db
```

Expected: 0 opened dangerous authorization pairs, 0 closed, 6 baseline pairs unchanged; 2 uses beyond intent. R1-R17 remain satisfied and the typo intent adds no access requirement. The check fails because the code now uses sensitive data beyond the stated purpose.

The code reader associates the detected database connection with the database named by the secret's `UNLOCKS` edge. The resulting code `CALLS` edge is classified as configured; the separate secret-to-database `UNLOCKS` edge is inferred. The reader does not need to understand the SQL statement to flag this use.

Expected headline: the PR says it fixes a typo, while its code now reads customer-db.

Evidence to inspect later: new calls in `services/support_portal/export.py`, route in `handler.py`, changed text in `views.py`, and the environment change in `terraform/services.tf`. Actual call line numbers wait for C1/C2 and the fixture.

P3 does not prescribe a new remediation candidate for this scenario. Reviewers must resolve the mismatch between intent and new sensitive-data use. Also, after this change the grant is used, so the baseline unused-grant conclusion must not simply be reused for the changed code.

## Intern capacity sketch

BIG = 1,000,000 protects every edge used to satisfy any legitimate requirement across the world, plus structural RUNS_AS/UNLOCKS/USES edges. It is not limited to Priya's requirements. USED = 1,000 marks otherwise-unprotected grants called by code; remaining edges cost 1.

```text
Priya
  | MEMBER_OF: BIG (I1)
support-engineers
  | CAN_ASSUME: BIG (I1, R1-R3)
prod-support
  +-- CAN read: BIG --> logs                  I1 / R1
  +-- CAN read: BIG --> invoices              R2 for Sam
  +-- CAN read: BIG --> DB secret             R3 for Sam / R4 for deploy
                         |
                         +-- UNLOCKS: BIG --> customer-db
```

The intern cut has Priya as source and invoices, secret, database as sinks. All ways to disconnect her dangerous targets require cutting a BIG edge. The simplified paper graph has a shared BIG bottleneck and gives a cut value of 1,000,000. Spec 02 says at least BIG; task E4 expects the exact value BIG. Runtime confirmation belongs to P1/E4.

Protecting only Priya's logs route would incorrectly make the invoice and secret grants cheap to delete. They also serve Sam and deploy, so deleting them would break other people's legitimate access. A new logs-only route for Priya solves that structural problem.
